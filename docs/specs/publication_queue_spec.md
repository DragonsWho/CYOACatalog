# ТЗ: Очередь публикаций (drip-feed авто-публикация)

> Статус: **обсуждённый дизайн, реализация позже.** Сначала доделываются статичные игры и обработка архивов в пайплайне — только потом берёмся за этот кусок.
> Архитектура зафиксирована (Вариант 1). Документ — готовое ТЗ для старта работ.

## 0. Цель
Модератор загружает в очередь сотни/тысячи одобренных игр (парсинг Reddit/4chan, архивы), а сервер сам публикует их по одной каждые ~2 часа (с разбросом), равномерно вкрапляя NSFW/SFW по их пропорции в очереди, при желании — раздельными темпами для статичных и интерактивных игр. Лента наполняется живо и автоматически, **не завися от того, включён ли локальный компьютер**.

## 1. Источники истины / терминология
- **Очередь** = записи коллекции `game_pipeline_state` со `state='approved'`. Эта коллекция admin-only (`listRule=null`) — обычные пользователи её не грузят вообще.
- **Публикация** = создание записи в коллекции `games` из записи очереди. `games` всегда содержит только опубликованные игры.
- **Статичная игра** — `img_or_link='img'` (длинные картинки-страницы CYOA). **Интерактивная** — `img_or_link='link'` (iframe на cyoa.cafe).
- **NSFW/SFW** — берётся из `game_pipeline_state.type`. В `games` отдельного поля нет (каталог ориентируется по тегу `nsfw`) — и не добавляем.
- `release_date` — **реальная дата создания игры** (для пользовательской сортировки «игры из 2020»). НЕ использовать под расписание.

## 2. Архитектура (Вариант 1)
```
Локальный пайплайн (s01..s0N)                      Сервер (Go + PocketBase)
download → parse → optimize → describe →            ┌────────────────────────────┐
screenshot → upload(R2) → awaiting_review           │ JSVM cron (тик 1–5 мин)    │
        │                                            │  читает publication_settings│
   веб-ревью модератора → state='approved'           │  если now>=next_publish_at: │
        │                                            │   выбрать 1 игру (баланс/   │
   НОВЫЙ шаг: дозалить в game_pipeline_state          │   shuffle) → создать games  │
   ВСЁ для публикации (скриншот-файл, файлы           │   (скопировать файл) →      │
   статичных страниц, resolved authors/tags,          │   state='published',        │
   img_or_link, description, release_date)            │   заполнить relation game   │
        ▼                                            │   → пересчитать next_publish │
   game_pipeline_state (state='approved') ──────────▶│                            │
   = ОЧЕРЕДЬ, самодостаточная для сервера             └────────────────────────────┘
                                                                  │
                                                                  ▼
                                                        games (только опубликованные)
                                                                  │ R2+CDN отдаёт картинки
                                                                  ▼  PB отдаёт текст+base64-плейсхолдеры
                                                            публичный каталог / FAISS
```
Ключевое следствие из текущего `s07_publish.py`: скриншот сейчас грузится мультипартом **с локального диска в момент публикации**. Для серверной авто-публикации всё нужное (включая файл обложки) должно оказаться в `game_pipeline_state` **до** постановки в очередь, пока локальная машина онлайн. Это и есть работа Фазы 1.

## 3. Модель данных

### 3.1 `games` — БЕЗ ИЗМЕНЕНИЙ
Ноль новых полей. Держим горячую таблицу постной (приоритет: слабый сервер, дешёвый хостинг). Имена существующих полей **не сокращаем** — экономия байт мизерная, а ломает фронт/Go/скрипт/FAISS.

### 3.2 `game_pipeline_state` — новые поля (Фаза 1)
Цель: к моменту `state='approved'` запись самодостаточна для серверной публикации без локального диска. Точный набор сверяется с тем, что POST-ит `s07_publish.py`.
| Поле | Тип | Назначение |
|---|---|---|
| `image` | file (single) | Обложка-карточка (`games.image`), бывший `screenshot.webp` с диска |
| `cyoa_pages` | file (multiple) | Страницы статичной игры (только static) |
| `cyoa_pages_preview` | file (multiple) | Превью страниц (только static) |
| `img_or_link` | select `img`/`link` | Статичная/интерактивная — нужно крону для разделения очередей |
| `description` | editor | Финальный HTML описания для публикации |
| `authors` | relation authors (multi) | **Разрешённые ID** авторов (резолвит пайплайн, не сервер) |
| `tags` | relation tags (multi) | **Разрешённые ID** тегов |
| *(уже есть, переиспользуем)* | | `title`, `source_url`→`original_link`, `hosted_url`→`iframe_url`, `release_date`, `type`(→nsfw), `state`, `game`(relation), `locked_until`/`locked_by` |

### 3.3 `publication_settings` — новая коллекция (singleton, admin-only)
| Поле | Тип | Дефолт | Назначение |
|---|---|---|---|
| `enabled` | bool | false | Глобальный вкл/выкл авто-публикации |
| `shuffle` | bool | true | Случайный выбор игры вместо FIFO |
| `balance_nsfw` | bool | true | Вкраплять NSFW/SFW по пропорции очереди |
| `separate_queues` | bool | false | Раздельные таймеры для static и interactive |
| `combined_interval_minutes` | number | 120 | Интервал общей очереди (separate=false) |
| `combined_jitter_minutes` | number | 30 | Разброс ± общей очереди |
| `combined_next_publish_at` | date | — | Запланированное время след. публикации |
| `combined_last_published_at` | date | — | Для дашборда |
| `interactive_interval_minutes` / `_jitter_minutes` / `_next_publish_at` / `_last_published_at` | | 120/30 | То же для очереди интерактивных (separate=true) |
| `static_interval_minutes` / `_jitter_minutes` / `_next_publish_at` / `_last_published_at` | | 120/30 | То же для очереди статичных (separate=true) |
| `publish_uploader` | relation users | — | Системный аккаунт-«загрузчик» для атрибуции `games.uploader` |

## 4. Алгоритм планировщика (JSVM cron)
Регистрируется `cronAdd("queue_publisher", "*/5 * * * *", handler)` в `pb_hooks/`. Частый тик + гейт по сохранённому времени (а не сам крон на 2ч) — чтобы джиттер, раздельные очереди, «опубликовать сейчас» и переживание рестартов были тривиальны.

На каждом тике (всё инлайн в одном хендлере — см. §9):
1. Прочитать `publication_settings`. Если `enabled=false` — выход.
2. Определить активные очереди: `separate_queues=false` → одна `combined`; иначе две — `interactive` и `static`.
3. Для каждой очереди, у которой `now >= next_publish_at`:
   1. Собрать `approved`-записи очереди (`combined` — все; иначе по `img_or_link`).
   2. Если пусто → ничего не публикуем; `next_publish_at` оставляем в прошлом (как появится одобренная игра — выйдет на ближайшем тике). Переход к следующей очереди.
   3. **Выбор типа (если `balance_nsfw`)**: взвешенно-случайно по остатку — `P(NSFW)=остаток_nsfw/(остаток_nsfw+остаток_sfw)`. Stateless: воспроизводит пропорцию очереди и равномерно вкрапляет, без счётчиков и без поля nsfw в `games`. Если `balance_nsfw=false` — тип не фильтруем.
   4. **Выбор игры**: среди кандидатов выбранного типа — случайная (`shuffle=true`) или старейшая по `created` (`shuffle=false`).
   5. **Лок** от гонки тиков: атомарно перевести запись `approved → publishing`, проставить `locked_by`/`locked_until`. Если не удалось (уже забрали) — взять следующую.
   6. **Материализация** (см. §4.1). Успех → `state='published'`, заполнить relation `game`, снять лок. Сбой → `state='failed'` + `error`, снять лок, **таймер не сдвигать, взять следующую игру на этом же тике** (один сбой не тормозит ленту).
   7. После успешной публикации: `last_published_at=now`, `next_publish_at = now + interval ± random(0..jitter)` (равномерно в `[interval−jitter, interval+jitter]`).

### 4.1 Материализация (создание `games`)
Повторяет то, что делает `s07_publish.py`, но читает из записи очереди, а не с диска:
- POST/создать `games`: `title`, `description`, `img_or_link`, `iframe_url`(=hosted_url) для link / `cyoa_pages`+`cyoa_pages_preview` для img, `original_link`, `release_date`, `uploader`(=`publish_uploader`), `authors`, `tags`.
- **Копирование файла(ов)** из `game_pipeline_state` в `games` внутри JSVM через локальный путь хранилища `pb_data/storage/{collectionId}/{recordId}/{file}` (`$filesystem`-хелпер) — без сети и без авторизации.
- **Идемпотентность как в s07**: искать существующую игру по `original_link`/title; если найдена с актуальной cyoa.cafe-ссылкой → skip; если со старой → PATCH (`iframe_url`, `original_link`), скриншот не трогать.

> ⚠️ **Риск №1 для валидации.** Копирование файла из записи в запись внутри JSVM — самое неизвестное место. **Первая задача реализации Фазы 2** — мини-спайк этого копирования на dev-копии БД, до всего остального.

## 5. API (всё moderator-only, по образцу `pb_hooks/pipeline_review.pb.js`)
- `GET  /api/pipeline/queue/status` — счётчики `approved` по `type × img_or_link`, `next/last_publish_at` по очередям, `enabled`.
- `GET  /api/pipeline/queue/settings` / `PATCH /api/pipeline/queue/settings` — чтение/правка настроек.
- `GET  /api/pipeline/queue/items?type=&page=` — пагинированный список очереди, **компактная проекция** под плейлист (без тяжёлых полей).
- `POST /api/pipeline/queue/publish-now[?type=]` — `next_publish_at=now` (выйдет на ближайшем тике).
- `POST /api/pipeline/queue/items/{id}/skip` — отложить (понизить приоритет / в конец).
- `POST /api/pipeline/queue/items/{id}/dismiss` — убрать из очереди (`state='dismissed'`).
- Пауза/продолжение — через `PATCH settings { enabled }`. «Перемешать» — отдельный эндпоинт не нужен (выбор и так случайный при `shuffle`).

## 6. UI — отдельная страница `/moderator/queue`
- **Панель настроек** (сверху): тумблеры `enabled`/`shuffle`/`balance_nsfw`/`separate_queues`; числовые интервал/джиттер (общий или по двум очередям); превью «следующая публикация ≈ ЧЧ:ММ (локально)».
- **Дашборд**: счётчики `approved` (static/interactive × NSFW/SFW); оценка темпа «≈ каждые N ч»; `last/next_publish_at`.
- **Плейлист**: пагинированные компактные строки (мелкий плейсхолдер, название, теги, короткое описание в узкую строку); по-строчные действия: «опубликовать сейчас», «пропустить», «убрать».
- Перф на этой странице не критичен (модератор-онли, не умножается на посетителей) — обычная пагинация, плейсхолдеры допустимы.

## 7. Перф-правила (область: ТОЛЬКО публичные пути)
Реальная грабля прошлого — не количество полей, а жадные/безлимитные запросы.
- Никаких `getFullList` без необходимости на публичных хот-путях; всегда пагинация.
- Никакого жадного `expand` всех тегов/авторов; разворачивать минимально нужное.
- `fields:`-проекции там, где поле не рисуется (не таскать лишнее).
- base64-плейсхолдеры — это **намеренная фича UX** (мгновенное размытое пятнышко в том же запросе, что и ссылки на R2-картинки) — оставляем как есть, это не нагрузка.
- Картинки/игры — R2 + Cloudflare CDN, на PB-сервер не давят; PB отдаёт только текст + плейсхолдеры.

## 8. Порядок работ
**Фаза 1 (сначала, вместе со статиками и архивами) — пайплайн.** К моменту `state='approved'` запись `game_pipeline_state` самодостаточна:
- [ ] добавить file-поле(я) и `img_or_link`/`description`/`authors`/`tags` в коллекцию (§3.2);
- [ ] локальный шаг: дозаливать скриншот-файл (и для статичных — файлы страниц) в запись очереди;
- [ ] построить аплоад **статичных** игр в PB (нового пути сейчас нет);
- [ ] резолвить и сохранять **ID** авторов/тегов (как уже делает s07 при POST).

**Фаза 2 — публикация.** Когда очередь самодостаточна:
- [ ] спайк копирования файла в JSVM (риск №1);
- [ ] коллекция `publication_settings`;
- [ ] cron-хук + логика выбора/баланса/джиттера/локов;
- [ ] эндпоинты `/api/pipeline/queue/*`;
- [ ] страница `/moderator/queue`;
- [ ] тест на копии БД → `make ship`.

## 9. Зависимости от пользователя (нужно перед кодом Фазы 1)
- Полный `s07_publish.py` — точные поля/файлы POST, чтобы перенести сборку payload на стадию раньше.
- Как сейчас обрабатываются/сортируются **статичные** игры локально (самый новый кусок).
- Список шагов пайплайна (s01..s0N) — куда вставить сборку publish-ready записи.
- Весь код (пайплайн + фронт + бэк) в одном месте.

## 10. PocketBase JSVM — ограничения (из `pb_hooks/pipeline_review.pb.js`)
Каждый `routerAdd`/`cronAdd`-хендлер исполняется в ИЗОЛИРОВАННОМ goja-рантайме: не видит ничего с верхнего уровня файла — **инлайнить всё** в хендлер. Доступны только инъецированные глобалы (`$app`, `$dbx`, `$apis`, `$filesystem`, `Record`, `e`, `console`).
- `record.get(field)` вместо `getBool/getString` (последние паникуют на Go-уровне).
- `$app.findAllRecords(col, $dbx.hashExp({...}))` вместо `findRecordsByFilter/findFirstRecordByFilter` (паникуют).
- Ошибки — `e.json(status, {...})` (а не `new BadRequestError/ForbiddenError`).
- Проверка модератора — `e.auth.get("isModerator")` с мягким сравнением (`=== true || == true || === 1 || String(v)==="true"`).
- Время — внутри в UTC, в UI показывать локально.
