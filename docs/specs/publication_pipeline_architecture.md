## Δ Ревью v2 (2026-06-10) — принятые изменения после независимой проверки

Прошли архитектуру через свежую модель (`publication_queue_review_request.md`).
Принято и впитано (детали правок схемы — в `PB/schema_changes_publication_queue.md`):

1. **Крон-исполнитель — на Go, не в JSVM.** Бинарь PB и так собирается (`make build`
   → `go build`, см. `hosting.go`). Копирование файлов очередь→`games` — через
   `core.Filesystem`. Снимает паники/изоляцию/отсутствие подстрочного поиска JSVM.
   Вердикт дедупа всё равно считаем на ноуте (pHash/тяжёлые либы); Go-крон исполняет.
2. **Фаза 0 ужата** до одного спайка — миграция блобов на R2 (спайк JSVM-копирования
   отпал).
3. **Идемпотентность — детерминированный `id`** (`games.id = queue.id`), а не поиск по
   `original_link`. Recovery записей в `publishing` по `findRecordById`. Без правок
   схемы `games`, без уникальных индексов.
4. **Внутриочередной дедуп:** слепки одобренных-но-неопубликованных пишутся в
   `asset_fingerprints` на стадии **approve**; Go-крон делает exact-чек перед `create`.
   При попадании → не авто-`update`, а «на повторное ревью».
5. **Состояние `publish_failed`** (N попыток → ждёт человека).
6. **Упрощения v1:** один таймер (убраны `separate_queues` и тройные интервалы);
   баланс NSFW = random pick из всей очереди (доля соблюдается сама).
7. **Одна база слепков** — истина в PB, ноут держит read-кэш (без двусторонней синхр.).
8. **>99 страниц** → разбиение на 2 записи `games`, связь через **существующую**
   `game_relationships` (id `pp3igro35qhi5e1`, уже UI-связана). `cyoa_pages`
   maxSelect=99 не поднимаем. Опц.: добавить значение `Part` в `relationship_type`
   (иначе `Sequel`+`order_in_series`).
9. **Безопасность/корректность:** view-правила до-ревью файлов очереди закрыть от
   публики; системный `uploader` защитить; `publish_mode=update` — белый список полей
   (никогда upvotes/comments/uploader).
10. **R2-миграция — `rclone`**, не `aws s3 sync` (CRC-чексуммы спотыкаются на R2).

✅ **Прод-схема сверена (2026-06-10):** `pb_schema.json` — полный экспорт. Коллекция
связей = `game_relationships` (id `pp3igro35qhi5e1`, UI-связана) → переиспользуем.
Остаётся сверить только версию PocketBase на сервере.

## 0. Главное в трёх абзацах

**Цель.** Мы разыскиваем игры пачками (Reddit/4chan/архивы/сабмиты), но
вываливать тысячу игр разом — скучно и подозрительно. Хотим, чтобы сервер сам
публиковал готовые игры по одной раз в ~2 часа (с разбросом), вкрапляя NSFW/SFW
по их доле, **независимо от того, включён ли ноут**. Лента сайта живёт сама.

**Что для этого нужно.** К моменту, когда игра встаёт «в очередь на публикацию»,
она должна быть **полностью готова и самодостаточна на сервере**: контент залит,
обложка лежит в базе (сейчас НЕ лежит — это главный технический долг), описание,
теги, тип, авторы — всё проставлено, дубль-проверка пройдена заранее. Тогда
сервер при публикации просто создаёт карточку в каталоге, ничего не вычисляя и
ничего не скачивая с ноута.

**Ключевое разделение ответственности.** Локальный пайплайн (ноут) — это «фабрика»:
качает, описывает, снимает скрин, проверяет на дубли, заливает контент, готовит
запись. Сервер — это «таймер выкладки»: берёт готовое и публикует по расписанию.
Дедуп и любые «умные» решения — **на ноуте, заранее**. Сервер их не повторяет.

## 1. Словарик (чтобы дальше было понятно)

- **PocketBase (PB)** — база данных + API сайта. Хранит каталог, пользователей,
  очередь обработки. Живёт на дроплете.
- **R2 / Cloudflare CDN** — облачное файловое хранилище Cloudflare. Раздаёт файлы
  быстро и со всех концов мира, не нагружая дроплет.
- **Хук / `pb_hooks/*.pb.js`** — серверный скрипт внутри PocketBase. На нём уже
  работает модераторская кнопка Approve.
- **JSVM / goja** — урезанный движок, на котором PB исполняет эти хуки. Часть
  обычных JS-команд там падает (см. §8) — поэтому серверный код пишем осторожно
  и проверяем спайками.
- **Cron-хук** — серверный скрипт, который PB сам запускает по расписанию
  (например, каждые 5 минут). Это и будет «таймер выкладки».
- **Спайк** — маленький разведочный эксперимент на копии базы: «а сработает ли
  вообще вот это?» — до написания настоящего кода.
- **Слепок / отпечаток (fingerprint)** — короткая «подпись» игры (хэш файла,
  pHash картинки, нормализованный URL, подпись текста), по которой мы узнаём,
  что две находки — на самом деле одно и то же. Основа дедупа.
- **Самодостаточная запись** — запись в очереди, в которой уже лежит ВСЁ для
  публикации (включая файл обложки), так что сервер опубликует её без ноута.

## 2. Как устроено сейчас (проверенные факты, не догадки)

### 2.1 Конвейер обработки (ноут, `CYOA Harvester/`)
Стадии `s01..s07` поверх явного состояния (`game_pipeline_state` в PB или
локальный `state.json`). Состояния:
`queued → downloaded → parsed → optimized → described → screenshotted →
uploaded → awaiting_review → approved → published` (+ `dismissed/rejected/failed`).

- `s06 upload` — зипует игру и льёт на **R2-хостинг** через `/api/hosting/admin/upload`
  (God Mode, под reserved-аккаунты). **Это происходит ДО ревью.** → К моменту
  `approved` интерактивный контент уже на R2+CDN, отдаётся с `slug.cyoa.cafe`.
- `s07 publish` (требует `approved`) — создаёт/обновляет запись в каталоге `games`:
  - ищет существующую игру по `original_link`/`iframe_url`/`title` (поиск по
    подстроке, оператор `~`);
  - если уже на нашем хостинге (`cyoa.cafe` в `iframe_url`) → **пропускает**;
  - если в каталоге, но ссылка внешняя → **обновляет** запись (наш URL в
    `iframe_url`, старый — в `original_link`) — НЕ создаёт новую (она у людей в
    избранном);
  - если в каталоге нет → создаёт новую: резолвит автора/теги по имени (создаёт
    при отсутствии), применяет логику SFW/NSFW (правила в `s07:247-271`), и
    **грузит обложку `screenshot.webp` мультипартом прямо с диска ноута**.

### 2.2 Главный технический долг (твой диагноз — точный)
**Обложка существует только на диске ноута до самой публикации.** В записи
очереди (`game_pipeline_state`) файла обложки НЕТ. Поэтому:
- модераторская панель не может показать скриншот (его негде взять);
- сервер не может опубликовать игру сам — обложку он взять неоткуда.

Это блокирует и ревью, и авто-публикацию. Чинится одинаково: **обложка (и для
статики — страницы) должна оказаться в записи очереди заранее, пока ноут онлайн.**

### 2.3 Два хранилища + кэш (проверено 2026-06-10)
1. **Файлы каталога PocketBase** — `games.image` (обложка), `games.cyoa_pages`
   (страницы статики), `games.cyoa_pages_preview`. Фронт берёт их по
   `/api/files/{коллекция}/{id}/{файл}` — **через сам PocketBase**.
   ✅ **Проверено: R2 в PB НЕ подключён → файлы каталога лежат на локальном диске
   дроплета.** (Settings → Files storage, тумблер S3 выключен.)
2. **R2-хостинг игрового контента** (`hosting.go`) — ZIP-рипы интерактивных игр,
   отдаются с поддоменов `slug.cyoa.cafe` напрямую с R2+CDN. Сюда статика сейчас
   **не попадает**.

**Кэш Cloudflare (проверено живым запросом + дашборд автора):**
- `/api/files/...` отдаёт `cache-control: max-age=2678400` (31 день) +
  stale-while-revalidate; реальный ответ — `cf-cache-status: HIT`, `age ~26 дней`.
- Дашборд: **97.29% запросов из кэша**, Cache Reserve включён (30-дневный TTL,
  ~16 ГБ), ~254 ГБ роздано за сутки при ~7 ГБ с ориджина.
- **Вывод: бандвич НЕ проблема — Cloudflare раздаёт ~97% картинок сам, дроплет в
  горячем пути почти не участвует.** Реальное узкое место — **место на диске
  дроплета** (тысячи тяжёлых статичных страниц его забьют → PB рискует упасть).

Поэтому «картинки игр» (хранилище 1) и «контент интерактива» (хранилище 2) — это
**разные** системы. Для интерактива контент уже на R2+CDN; для обложек/статики —
пока на диске дроплета. Решение — §7 (подключить R2 как хранилище PB).

### 2.4 Статика (`tools/static_moderation/`)
Сканер собрал ~4259 статичных игр в локальный `static_index.json`. Модерка `app.py`
сейчас — **чисто локальная триажа** (статусы pending/approved/rejected/rework
в локальном файле). **Пути в PB у статики нет вообще** — ни в очередь, ни в каталог.
То есть «решить со статикой» = спроектировать и построить недостающий путь, а не
доработать существующий.

### 2.5 Дедуп (сейчас дырявый)
- `precheck` сверяет с каталогом **только записи в состоянии `queued`** — игры,
  попавшие дальше мимо `queued`, проскакивают (инцидент 2026-05-28: 10/10 зря
  перезалили).
- Контентный дедуп есть в отдельных тулах (`dedup_fingerprint/`, pHash-плитки),
  но он **не интегрирован как гейт** и не имеет единой общей базы слепков.

## 3. Целевая модель: три стадии-очереди (твоя картина)

Ты описала это как три очереди — закрепляю их как стадии **одной** записи
`game_pipeline_state`, чтобы не плодить коллекции:

```
 СТАДИЯ 1: НАХОДКИ            СТАДИЯ 2: ОБРАБОТКА            СТАДИЯ 3: ОЧЕРЕДЬ ПУБЛИКАЦИИ
 («предложения»)             (ноут — «фабрика»)             (сервер — «таймер»)
 ─────────────────           ──────────────────            ────────────────────────
 любая найденная ссылка:     download→parse/OCR→optimize→   готовые, полностью
  • reddit/4chan скрипт      describe→tags→screenshot→      оформленные игры ждут
  • архивы (allsync и т.п.)  ДЕДУП-ГЕЙТ→upload(R2)→          своего часа; сервер сам
  • сабмиты пользователей    положить ВСЁ в запись→          выкладывает по 1 раз
                             модерка(человек)→approved      в ~2ч (NSFW/SFW баланс)
 state: queued              state: downloaded..awaiting_    state: approved → publishing
                                   review                         → published
```

- **Стадия 1 (находки).** Уже частично есть: хук `/api/pipeline/submit` создаёт
  запись `queued`; reddit/4chan-тулы дают ссылки. Здесь же — первичный лёгкий
  дедуп по нормализованному URL (чтобы не обрабатывать одно и то же дважды).
- **Стадия 2 (обработка, ноут).** Вся «фабрика». **Дедуп-гейт — здесь** (§4).
  В конце стадии запись становится **самодостаточной** (§5) и уходит на модерку.
  Человек одобряет → `approved`.
- **Стадия 3 (очередь публикации, сервер).** Только `approved`-записи. Сервер по
  расписанию берёт по одной и публикует (§6). **Никакого дедупа и вычислений
  здесь нет** — всё решено на стадии 2.

Почему одна коллекция, а не три: переход между стадиями — это смена поля `state`,
а не переезд между таблицами. Дешевле, атомарнее, уже так работает.

## 4. Дедуп как отдельная подсистема: единая база слепков

Твоя идея — **единая база отпечатков, общая для ноута и сервера** — берётся за
основу. Это правильно и закрывает дыру §2.5.

### 4.1 Принцип
- Дедуп — **гейт на стадии 2**, до того как игра дойдёт до `approved`.
- На стадии 3 (публикация) дедупа НЕТ. Сервер исполняет уже принятое решение.
- Решение «новая / обновить существующую / дубль-пропустить» **запекается в запись
  заранее** (поле вердикта — см. §5), чтобы серверу не нужно было искать по
  каталогу (а в JSVM надёжный поиск по подстроке сложен — §8).

### 4.2 Что хранит база слепков (на каждую игру/ассет)
- **Нормализованный URL** оригинала (без `web.archive.org/...`, без хвостового
  слэша, в нижнем регистре) — дешёвый точный матч.
- **md5 файлов** — байт-в-байт дубли.
- **pHash-плитки** картинок (`phash_tiles` + `ntiles`) — против пересжатий и
  ре-скейлов; главный сигнал для статики и обложек.
- **Подпись текста** (для интерактива — из извлечённого текста) — опционально.
- **Ссылка на запись каталога** (если игра уже опубликована) или метка-надгробие
  (отклонена/мусор), чтобы дубли отсеивались даже без записи в `games`.

### 4.3 Где она живёт (ответ на «локально и на сервере»)
- **Истина — на сервере, в PB**, в новой коллекции (рабочее имя `asset_fingerprints`,
  поля близки к SPEC статики §2). Почему в PB: вердикты невосстановимы, это
  решения людей; нужны и серверу, и любому клиенту.
- **Локально — горячее зеркало** этой коллекции (быстрый файл-индекс) для ночного
  прогона на ноуте без тысяч запросов к серверу. Перестраивается из PB.
- Так выполняется твоё «единая база, по ней сверяются все новые находки»: ноут
  сверяется с зеркалом, сервер/клиенты — с коллекцией, обе — одна правда.

### 4.4 Каскад проверки (от дешёвого к дорогому)
1. нормализованный URL (мгновенно) →
2. md5 (точные дубли) →
3. pHash-плитки в пределах аспект-бакета (порог ~0.10) — **жёсткий гейт** →
4. эмбеддинги — **только подсказка человеку** в модерке («похоже на X»), НЕ
   автоотбой (разные игры на одну тему дают высокое сходство).

> ⚠️ Предусловие «боевого» гейта — **бэкфилл**: отпечатать существующий каталог
> (часть статики уже скачана; чего нет — докачать). До бэкфилла гейт работает в
> режиме подсказки, не блокировки.

## 5. Самодостаточная запись очереди (Фаза 1 — фундамент)

Чтобы сервер мог опубликовать без ноута, к моменту `approved` запись
`game_pipeline_state` должна содержать ВСЁ. Сейчас не содержит. Нужно:

### 5.1 Новые поля на `game_pipeline_state` (⛔ изменение схемы → ревью автора)
| Поле | Тип | Зачем |
|---|---|---|
| `image` | file (single) | Обложка-карточка (то, что сейчас `screenshot.webp` на диске). **Закрывает главный долг §2.2.** |
| `cyoa_pages` | file (multiple) | Страницы статичной игры (только static) — **если** статика идёт через очередь (§7, развилка). |
| `cyoa_pages_preview` | file (multiple) | Превью страниц статики. |
| `img_or_link` | select `img`/`link` | Статика vs интерактив — нужно для раздельных очередей и для публикации. |
| `description` | editor | Финальное HTML-описание для каталога (каталожное, НЕ rich-для-эмбеддингов). |
| `authors` | relation→authors (multi) | **Уже разрешённые ID** авторов (резолвит ноут, не сервер). |
| `tags` | relation→tags (multi) | **Уже разрешённые ID** тегов (включая SFW/NSFW — логика правил `s07` переносится на ноут). |
| `image_base64` | text | Размытый плейсхолдер обложки (`games.image_base64`) — фронт рисует его мгновенно. Тоже надо стейджить. |
| `nsfw` | bool | Нормализованный тип для баланса очереди (вместо неоднозначного текстового `type`). |
| `publish_mode` | select `create`/`update`/`skip` | **Вердикт дедупа**, запечённый на стадии 2. Сервер просто исполняет. |

Уже есть и переиспользуется: `slug`, `original_url`/`source_url` (→`games.original_link`),
`hosted_url` (→`games.iframe_url`), `title`, `release_date`, `state`,
`locked_until`/`locked_by`, `data`(json). **`game`(relation→games) переиспользуем
как dedup-таргет**: для `update`/`skip` дедуп стадии 2 кладёт в него существующую
запись каталога; для `create` оно заполняется результатом после публикации. Новое
поле `target_game` НЕ нужно. `uploader` берётся из `publication_settings`, не на запись.

> ⚠️ Цель — чтобы поля очереди **зеркалили публикуемые поля `games`**, и серверу
> оставалось «скопировать запись». Поля `games`, которые НЕ стейджим: `uploader`
> (из настроек), `upvotes*`/`comments*` (накопительные, стартуют пустыми), `files`
> (пайплайн не использует). Точный apply-список — `PB/schema_changes_publication_queue.md`.

### 5.2 Новый локальный шаг пайплайна (ноут): «подготовка к очереди»
Между `screenshot` и `awaiting_review` (≈ заменяет no-op `s06b_review_gate`):
1. залить файл обложки в `image` записи очереди (и для статики — `cyoa_pages` +
   `cyoa_pages_preview`);
2. перенести логику `s07` на этот шаг: резолв авторов/тегов в **ID**, применение
   правил SFW/NSFW → `tags` + `nsfw`, финальное `description`, `img_or_link`;
3. прогнать дедуп-гейт (§4) и записать `publish_mode` + `target_game`.

После этого запись самодостаточна. Модератор одобряет → `approved`. `s07` на ноуте
больше не нужен для авто-ленты (остаётся для ручных разовых случаев).

## 6. Серверная авто-публикация (Фаза 2 — «таймер»)

### 6.1 Новая коллекция `publication_settings` (singleton, admin-only)
Тумблеры и таймеры (по «Варианту 1», `temp/очередь.md` §3.3): `enabled`,
`shuffle`, `balance_nsfw`, `separate_queues`, интервал/джиттер (общий или
раздельно static/interactive), `*_next_publish_at`/`*_last_published_at`,
`publish_uploader` (системный аккаунт для `games.uploader`).

### 6.2 Cron-хук (тик каждые ~5 мин, гейт по сохранённому времени)
На каждом тике: читаем настройки; если `now ≥ next_publish_at` — выбираем одну
игру из `approved` (баланс NSFW/SFW по остатку очереди, случайно/FIFO), атомарно
переводим `approved → publishing` (защита от гонки), **исполняем `publish_mode`**:
- `create` → создать запись `games`, **скопировать файл обложки** из записи
  очереди в `games.image` (для статики — страницы);
- `update` → пропатчить `target_game` (наш `iframe_url`, `original_link`);
- `skip` → ничего не создавать, просто закрыть запись.

Успех → `state='published'`, заполнить `game`, снять лок, пересчитать
`next_publish_at = now + интервал ± джиттер`. Сбой → `state='failed'` + `error`,
таймер не двигать, взять следующую на этом же тике (один сбой не тормозит ленту).

### 6.3 Изменение схемы для этого (⛔ ревью)
- Добавить значение **`publishing`** в select `state` (сейчас его в enum НЕТ).

### 6.4 API + страница модератора `/moderator/queue`
Эндпоинты `/api/pipeline/queue/*` (status/settings/items/publish-now/skip/dismiss)
и UI: панель настроек, дашборд счётчиков, пагинированный плейлист с построчными
действиями. Перф-критичность низкая (только модератор). Детали — «Вариант 1» §5–6.

## 7. Хранилище и статика (решено 2026-06-10)

### 7.1 Решение по хранилищу: подключить R2 как бэкенд PB (Вариант 2)
Дано (§2.3): R2 в PB не подключён → всё на диске дроплета; Cloudflare кэширует
`/api/files` на 31 день с 97% попаданий. Узкое место — диск, не трафик.

| Вариант | Диск дроплета | Трафик | Фронт | Вердикт |
|---|---|---|---|---|
| 1. Как сейчас (локальный диск) | ❌ забьётся статикой | ок (CF) | — | плохо масштабируется |
| **2. R2 как S3-хранилище PB** | ✅ файлы на R2 | то же (CF) | **без изменений** | ✅ **выбрано** |
| 3. `images.cyoa.cafe/...` напрямую с R2 | ✅ | чуть лучше на ~3% промахов | переделка | избыточно сейчас |

**Выбран Вариант 2.** Включить S3-хранилище в PB (Settings → Files storage),
указать R2-бакет. Эффект:
- обложки + страницы статики переезжают с диска дроплета на R2 (диск разгружен);
- **фронт не меняется** — он по-прежнему запрашивает `/api/files/...`, PB отдаёт
  байты с R2;
- кэш Cloudflare работает идентично (заголовок `cache-control` на ответе
  `/api/files` не зависит от того, откуда PB взял файл);
- egress R2→Cloudflare бесплатный.

Вариант 3 (твоя идея `images.cyoa.cafe/...`, как у интерактив-хостинга) «чище» по
CDN — на промахах кэша вообще минует дроплет, — но требует **переделки фронта**
(он рисует страницы из файловых полей PB, а не по внешним URL) и заводит **третий**
механизм хранения. При кэше 97% выгода мизерна → отложено. Вернуться, если дроплет
начнёт задыхаться по CPU.

> ⚠️ Подключение R2 к PB меняет §8/риск №1: серверное копирование файла обложки
> станет «копированием внутри R2-хранилища» через файловый слой PB. **Спайк
> обязателен** именно в этой конфигурации (S3-бэкенд), не на локальном диске.

### 7.2 Решение по статике: ГОТОВАЯ архитектура сразу, без висячих хвостов
**Решение автора (2026-06-10): всё для статики делаем СЕЙЧАС, за один проход.**
Никаких «доделаем потом, когда дойдём до статики» — это копится недоделанным.

- **Схема PB готовится полностью под оба типа в ОДИН проход** (см. §5.1 и
  `PB/schema_changes_publication_queue.md`): очередь зеркалит публикуемые поля
  `games`, включая `cyoa_pages`/`cyoa_pages_preview`/`image_base64`/`img_or_link`.
  Раз `games` уже умеет статику — очередь обязана уметь так же, чтобы серверу
  осталось «скопировать запись».
- **Сервер (cron) сразу умеет публиковать оба типа** — ветка `img`/`link` по
  `img_or_link` (для `link` копирует обложку + ставит `iframe_url`; для `img`
  копирует страницы+превью+обложку). Пишем сразу, не во второй заход.
- Единственное, что объективно последовательно, — **наполнение** статикой: для
  этого нужен статичный пайплайн (OCR→описание→теги), он отдельный воркстрим
  (`tools/static_moderation/` сейчас локальная триажа, §2.4). Но **PB-сторона и
  серверная публикация статики готовы с первого дня** — когда статичный пайплайн
  начнёт класть записи в очередь, всё уже работает, дорабатывать в PB ничего не надо.

## 8. Риски и спайки (объяснено просто)

1. **Спайк копирования файла в JSVM (риск №1).** Серверу нужно переложить обложку
   из записи очереди в запись каталога. Внутри урезанного движка это самое
   неизвестное место — особенно если файлы на R2 (тогда «копировать по локальному
   пути» не сработает, нужен способ через файловый слой PB). **Проверяем на копии
   базы до всего остального.** Зависит от §9.1.
2. **Поиск/дедуп в JSVM.** В этой сборке PB надёжный поиск по подстроке URL ломается
   (`findRecordsByFilter` падает; работает только точное равенство). **Поэтому
   §4: дедуп делаем на ноуте заранее, сервер не ищет.** Это снимает риск.
3. **Хранилище статики.** Тысячи тяжёлых страниц. Решается выбором пути §7 +
   включением S3-хранилища PB (§9.1).
4. **Атрибуция и идемпотентность.** Системный аккаунт-загрузчик; `publish_mode`
   гарантирует, что повтор тика не задвоит запись.

### 9.2 ✅ Cloudflare кэширует `/api/files/...`
Подтверждено: `cache-control: max-age=2678400`, `cf-cache-status: HIT`, 97.29%
попаданий, Cache Reserve включён (§2.3). Бандвич не проблема; узкое место — диск.

### 9.3 ⏳ Объём статики (уточнить перед Фазой 1-static)
~4259 игр в `static_index.json`; прикинуть средний вес страниц → оценка R2-хранилища
и времени заливки. Не блокирует старт (интерактив-первым).

### 9.4 ✅ Бакеты R2 (решено 2026-06-10)
- PB хранит **ВСЕ** файлы коллекций в **ОДНОМ** бакете (единая настройка Files
  storage). Разнести «статика отдельно, скриншоты отдельно» внутри PB **нельзя** —
  это только Вариант 3 (отложен). Поэтому: **1 новый бакет под все файлы каталога
  PB** (обложки + страницы статики + стейджинг очереди) + существующий бакет
  хостинга (`R2_BUCKET_NAME`). Итого 2 бакета.
- **Цена не зависит от числа бакетов** — биллинг по объёму (ГБ-мес) + операции;
  egress R2→Cloudflare бесплатный; free-tier (10 ГБ / 1М запись / 10М чтений в мес)
  общий на аккаунт. Чтения из R2 — только на ~3% промахов кэша.

### 9.5 ⚠️ Миграция существующих файлов на R2 (PB сам НЕ переносит)
Переключение PB на S3 действует только на **новые** загрузки; старые блобы
остаются на диске → битые картинки, если не перенести. Однократная операция:
1. создать бакет, получить S3-credentials;
2. `rclone`/`aws s3 sync` скопировать `pb_data/storage/*` в бакет (сохранив
   структуру `storage/{collectionId}/{recordId}/{file}`);
3. включить S3 в PB Settings → Files storage, проверить, что картинки грузятся;
4. только потом удалять локальные копии.
Сначала прогон на копии. На проде — в окно обслуживания.

### 9.6 ⚠️ Версия PocketBase (локальная ≠ серверная)
Локальный PB давно не обновлялся, может расходиться с сервером. Перед правками
схемы и спайками — **сверить версию сервера** (футер админки / `/api/health`),
спайки гонять на копии **серверного** `pb_data` под **серверным** бинарём PB.
Формат schema-JSON, S3-настройки и JSVM-API между версиями отличаются.
